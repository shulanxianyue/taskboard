# TaskBoard — initial security notes
| Question | Our answer |
| --- | --- |
| What data does the application handle? | Task records contain a title, optional description, status, and server-assigned integer ID. They are held in a process-local in-memory dictionary; there is no user identity or persistent database integration yet. |
| Who should be able to create, update or delete a task? | No authentication or authorization is implemented. Any client that can reach the API can currently create, update, and delete tasks. Before production or exposure to untrusted networks, restrict these actions to authenticated, authorized users. |
| Which inputs come from users? | JSON task fields (`title`, `description`, `status`) on create and patch requests, and the `task_id` path parameter on get, patch, and delete requests. |
| What abuses are possible today? | An unauthenticated reachable client can alter or delete any task because there are no ownership checks. Clients can also create tasks without a count limit, consuming memory; there is no rate limiting. Field sizes and status values are validated, but data is lost when the process restarts. |
| What secrets could appear in this project later? | Credentials embedded in `DATABASE_URL`, a production `SECRET_KEY`, and future service/API tokens. Keep real values in local or managed secret storage, never in source control; `.env` is ignored by `.gitignore` and `.env.example` contains placeholders only. |
| Which controls already exist, and which test proves each? | Pydantic schemas reject unknown fields and constrain title/description lengths and status; `test_client_cannot_set_id`, `test_blank_title_is_rejected`, `test_title_too_long_is_rejected`, and `test_invalid_status_is_rejected` cover key cases. `TaskId` rejects non-positive IDs (`test_non_positive_id_is_rejected`); missing tasks return 404 (`test_unknown_id_returns_404`). There are no tests or controls for authentication, authorization, rate limits, or task-count limits. |
| What automated control should we add next? | Add a CI check on pull requests that installs `requirements.txt` and runs `pytest`; make it required before merging. Then add automated dependency vulnerability scanning. |
